# Project flow (`flow.get`, capability `project_flow_v1`)

How a project — or a lone chat — advanced, and how the agent took part, as a
sequence of **stages** the desktop draws as a stepper and the CLI prints as a
table (`rinari flow`). The projection is the engine's: the desktop never
recomputes it from `session.timeline` calls, so both clients agree and no
logic is duplicated.

## Facts, not estimates

Everything is derived from persisted records:

| Source | What it contributes |
|---|---|
| `turn.started` / terminal turn events | mode, status, times, user message, peer provenance |
| `model.started` | executor models (`model` ref), counted per stage |
| `model.content.completed` (final, PLAN) | the stage title (first Markdown heading, else first line) |
| `agent.started` | subagents that ran, counted per stage |
| `turn.changes.completed` | files touched (path + kind), capped at 8 per stage with `files_more` |
| `verification.completed` | `done` counts as passed; `failed`/`partial`/`blocked` as failed |
| `approval.*` / `question.*` | unresolved requests of a **running** turn → `needs_you` |
| task graph (`tasks.tree`) | progress of BUILD stages, summary counts |
| checkpoints | count per stage window |

Nothing is generated by a model, and what is unknown is `null` (the desktop
prints "sin datos"). A moved or deleted project folder degrades `tasks` to
`null` instead of failing.

## Stage rule

Turns of every session in the scope are ordered by `started_at`. A stage is a
contiguous run of turns with the same mode:

| Mode | `kind` |
|---|---|
| `plan` | `planning` |
| `review` | `review` |
| anything else | `implementation` |

A `planning` stage opens a **cycle** (`cycle_index`); the stages that follow
belong to it until the next PLAN. A scope that starts in BUILD is cycle 1.

## Status and progress

| Field | Rule |
|---|---|
| `status` | a running turn → `active` (or `needs_you` with an unresolved approval/question); otherwise by the last turn: `completed` → `done`, `failed` → `failed`, cancelled/stopped → `stopped`. |
| `progress` (`planning`) | `1.0` when done, else `null`. |
| `progress` (`implementation`) | `done / touched` over the tasks created or updated inside the stage window; without touched tasks, `1.0` only when the stage is done, else `null`. |
| `progress` (`review`) | `passed / (passed + failed)` of the verification outcomes, else `null`. |
| `summary.progress` | turn-weighted mean of the non-null stage progresses, else `null`. |

## Request / result

```jsonc
{ "project_id": "proj_…" }   // or
{ "session_id": "ses_…" }    // exactly one; both or none → INVALID_PARAMS
```

A project scope covers every session that references the project by id or,
for sessions created before the project was registered, by root snapshot.
Closed and archived sessions are included: their history is part of the flow.

Result definitions (`flowResult`, `flowSummary`, `flowStage`, …) are listed
in `x-codegen-definitions` of `schema/v1.json`, so Rinari Agent generates its
DTOs from them. Each stage carries an `anchor` (`session_id`, `turn_id`) to
reveal the turn that opened it.

## Events

No new event. Clients refresh `flow.get` when a turn of a session in the
scope starts or ends, when a changeset or verification completes, or when an
approval/question is requested or resolved.

## Acceptance (`tests/unit/test_engine_flow.py`)

Fact folding per turn; unresolved interventions only on running turns; peer
provenance; excerpt/heading stripping; contiguous stages across interleaved
sessions with PLAN cycles; honest status for running/failed/stopped/recovered
stages; progress never invents a number; payload shape (executors, agents,
sessions, files cap, checkpoints, anchor, summary); empty scope; protocol
round trip on a real project with two sessions and a scripted model;
parameter validation and `NOT_FOUND`; degradation when the folder is gone;
capability announced.
