# Project flow (`flow.get`, capability `project_flow_v1`)

How a project — or a lone chat — advanced, and how the agent took part, as a
sequence of **stages** the desktop draws as a stepper and the CLI prints as a
table (`rinari flow`). The projection is the engine's: the desktop never
recomputes it from `session.timeline` calls, so both clients agree and no
logic is duplicated.

## Facts, not estimates

Everything is derived from persisted records:

| Source | What it contributes |
|---|---|
| `turn.started` / terminal turn events | mode, status, times, user message, peer provenance |
| `model.started` | executor models (`model` ref), counted per stage |
| `model.content.completed` (final, PLAN) | the stage title (first Markdown heading, else first line) |
| `agent.started` | subagents that ran, counted per stage |
| `turn.changes.completed` | files touched (path + kind), capped at 8 per stage with `files_more` |
| `verification.completed` | `done` counts as passed; `failed`/`partial`/`blocked` as failed |
| `approval.*` / `question.*` | unresolved requests of a **running** turn → `needs_you` |
| task graph (`tasks.tree`) | progress of BUILD stages, summary counts |
| checkpoints | count per stage window |

Nothing is generated by a model, and what is unknown is `null` (the desktop
prints "sin datos"). A missing project folder, or one without a Git
repository, is checked as a **precondition** before asking, so `tasks` and
`checkpoints` degrade to "no data" without swallowing anything else: a
corrupt database or a denied permission propagates instead of being
presented as a project with no data.

## Stage rule

Turns of every session in the scope are ordered by **instant** — ISO-8601
parsed to UTC, with `turn_id` as a stable tie-break. String comparison is not
enough: `Z` and `+00:00` are the same moment and sort differently. A date
that cannot be parsed is an unknown fact and sorts last instead of first.

A stage is a contiguous run of turns with the **same mode**. `kind` is
presentation only:

| Mode | `kind` |
|---|---|
| `plan` | `planning` |
| `review` | `review` |
| anything else (`ask`, `agent`, `full-access`, …) | `implementation` |

The boundary is the mode, **not** `kind`: `ask`, `agent` and `full-access`
share `implementation` and are different modes, so three contiguous turns of
those modes are three stages. A turn without a declared mode gets the
explicit `unknown` mode rather than joining the previous stage.

A `planning` stage opens a **cycle** (`cycle_index`) when it **starts**, so
the cycle in progress can be shown while planning. The stages that follow
belong to it until the next PLAN. A scope that starts in BUILD is cycle 1.

## Status and progress

| Field | Rule |
|---|---|
| `status` | a running turn → `active` (or `needs_you` with an unresolved approval/question); otherwise by the last turn: `completed` → `done`, `failed` → `failed`, cancelled/stopped → `stopped`. |
| `progress` (`planning`) | `1.0` when done, else `null`. |
| `progress` (`implementation`) | `done / touched` over `current_task_snapshot`, and **only while the stage is alive**. A finished build stage is `null`, even without tasks: that a turn ended says nothing about how much of the work got done. |
| `progress` (`review`) | `passed / (passed + failed)` of the verification outcomes, else `null`. This is the **share of checks that passed**, not a percentage of time elapsed: a finished stage with one of two checks passing is `0.5`. |
| `summary.progress` | `null` if **any** stage is unknown. A mean over only the known stages reported 100 % while a build was still running. |
| `summary.progress_coverage` | `known_stages` / `total_stages` and `partial_progress`: the mean over what is known, labelled as partial and never presented as a total. |
| `turns_failed`, `turns_stopped` | per stage. A stage that failed and then recovered ends as `done`; these keep the record that it had incidents. |

### `current_task_snapshot` is the present, not the past

Membership of a task in a stage is decided by `created_at`/`updated_at`, but
the status comes from the **current** graph. A task created in one stage and
finished much later would otherwise rewrite that stage's percentage
retroactively. So the field is named for what it is, and it only feeds
`progress` while the stage is alive — where "now" and "then" are the same
thing. It is never used to fabricate past progress.

## Request / result

```jsonc
{ "project_id": "proj_…" }   // or
{ "session_id": "ses_…" }    // exactly one; both or none → INVALID_PARAMS
```

A project scope covers every session that references the project by id or,
for sessions created before the project was registered, by root snapshot.
Closed and archived sessions are included: their history is part of the flow.

Result definitions (`flowResult`, `flowSummary`, `flowStage`, …) are listed
in `x-codegen-definitions` of `schema/v1.json`, so Rinari Agent generates its
DTOs from them. Each stage carries an `anchor` (`session_id`, `turn_id`) to
reveal the turn that opened it. The DTOs are closed
(`additionalProperties: false`) and ids, titles, excerpts, paths and arrays
are bounded in the schema **and** at runtime — the schema validates what was
already built, so a bound that lives only there still lets the big response
be assembled first.

## Bounds and paging

A flow cannot grow without limit: `NdjsonTransport` cuts at 16 MiB and a line
past that does not return an error, it takes the stream down.

- at most `MAX_STAGES` (200) stages per response, the **most recent** ones;
- `truncated` and `stages_omitted` say when history is missing — silent
  truncation is what the old global 500-session limit did;
- `next_cursor` is the **id** of a stage, not an index: indices are recomputed
  on every projection, so they are not a stable cursor. Pass it back as
  `before` to walk further back;
- `summary` always describes the **whole** flow, not the page;
- per stage: 8 files (`files_more`), 32 sessions (`sessions_more`), 16
  executors and 16 agents.

Sessions of a project are queried by id or legacy root snapshot, without a
global limit, and only the sixteen event types the projection actually reads
are loaded. A projection is cached per scope and keyed by `revision`, so a
burst of refreshes does not refold the whole history.

## Revision and invalidation

`flowResult.revision` is a fingerprint of the scope: which sessions belong to
it, how far each one's events go, and the shape of tasks and checkpoints. It
covers sessions **with no turns**, which is what lets a client notice a newly
created session that has not produced anything yet — membership cannot be
deduced from the stages, because a session without turns appears in none.

A response carrying an older revision must not replace a newer one.

Clients refresh when a turn of a session in the scope starts or ends, when a
changeset or verification completes, or when an approval/question is
requested or resolved. For facts that change **outside** a turn — where no
activity event would reveal them — the engine emits `flow.invalidated`
(`root`, `project_id`, `reason`). Today that is `checkpoint.restore`; a
preview changes nothing and stays quiet. The event carries the scope and the
reason, not the projection: it is a signal to ask again, and computing the
flow for someone who may not be looking at it would be wasted work.

## Acceptance (`tests/unit/test_engine_flow.py`)

Fact folding per turn; unresolved interventions only on running turns; peer
provenance; excerpt/heading stripping; contiguous stages across interleaved
sessions with PLAN cycles; honest status for running/failed/stopped/recovered
stages; progress never invents a number; payload shape (executors, agents,
sessions, files cap, checkpoints, anchor, summary); empty scope; protocol
round trip on a real project with two sessions and a scripted model;
parameter validation and `NOT_FOUND`; degradation when the folder is gone;
capability announced.
